# SPEC deviations

Each owner appends its own section. Keep entries short: what changed, and why.

## Owner A (plugin shell)

1. **`marketplace.json` has a top-level `description`.** `claude plugin validate --strict` validates the marketplace manifest too and fails with "No marketplace description provided" without it (plugin-marketplaces.md, validation warnings).
2. **toggle.sh rejects `on` / bare toggle without `CLAUDE_CODE_MESSAGING_SOCKET` even when the daemon is already running.** SPEC §5.7 only checks it on the spawn path, but binding an owner with no socket is useless either way.
3. **toggle.sh passes the daemon's reply through only if it is one line, starts with `{`, ends with `}` and contains `"continue":false`.** Otherwise a JSON error body (e.g. 403 `{"error":…}`) would be printed as-is, the prompt would not be stopped, and the skill's fallback body would reach the model. Such replies produce the §9.1 "did not answer" message instead.
4. **Foreign sotto daemon on our port (other `data_dir` / `plugin_root`):** for every action toggle.sh uses *that* daemon's key (`<its data_dir>/daemon.key`), not only for `shutdown`, so `/talk status|off` from another install still works. If it has not stopped 1.5 s after `shutdown`, toggle.sh reports "did not answer" (pointing at the other daemon's log) instead of spawning into a busy port.
5. **After a spawn, `/healthz` must report our `data_dir`**, not merely `"name":"sotto"`, before toggle.sh talks to it.
6. **Spawn poll deadline:** bash 3.2 (macOS `/bin/bash`) has no sub-second clock, so the "every 50 ms for up to 3 s" poll is bounded by `SECONDS < 3` (2 to 3 s of wall time) plus a 60-iteration cap. Measured cold-start failure path: about 3 s.
7. **`session` object:** always sent (all actions), with empty fields omitted rather than sent as `""`. `claude_pid` is sent only when `CLAUDE_PID` is all digits.
8. **Numeric config values** accept decimals (`"2.50"` → `2.5`) within range; the port must be an integer (`"47821.0"` is accepted as 47821). Owner B: `idle_minutes` / `daily_cap_minutes` may therefore be non-integers.
9. **hook.sh details** (behaviour-preserving):
   - first line is `exec 2>/dev/null` (a builtin redirection, no fork) so a stray error can never reach stderr;
   - the exit status of the gate's `read` is ignored (it is non-zero when `active` lacks a trailing newline) and emptiness of `OWNER` is checked instead; `PORT` must be all digits;
   - the body is sent with `printf '%s' "$INPUT" | curl --data-binary @-` instead of `<<<"$INPUT"`, so no newline is appended (the body equals stdin minus trailing newlines stripped by `$(cat)`);
   - the context JSON is printed without a trailing newline.
10. **No separate session-end script.** The orchestrator brief mentioned one; SPEC §5.4 routes SessionEnd through `hook.sh SessionEnd` (forward only), which is what is implemented.

## Owner C (web page)

1. **`Space` also toggles mute while live** (SPEC §7.5 gives `Space` only for resume). The build brief asked for "spacebar/M". `Space` is ignored while a button, link or form control has focus, so it never double-fires with a focused button's own activation.
2. **Mic picker has an "Automatic" entry** (value `""`, which clears `clv.inputDeviceId`) so a user can return to the §7.5 default-mic rules after picking a device. The speaker picker's `""` entry is "System default".
3. **One active window per browser profile** (`BroadcastChannel("sotto")`): a newer sotto page takes over. The older page POSTs `pause` if it held a session, closes its event stream, and shows "Voice moved to another window". This prevents two pages from both answering `command:"connect"` (for example, a default-browser tab left open plus a new app window).
4. **The page re-bootstraps on every event-stream error**, not only on the first load. A restarted daemon has a new page token, and EventSource never retries after a 403. If the token changed while the page held a peer connection, the page sends `session.close`, then tears down, because the new daemon has no sideband for the old session.
5. **Page-initiated `session.close` waits up to 2 s for `session.closed`** before tearing down (daemon restart and the 20 s lost-contact case). The unload path cannot wait and sends it without waiting, as specified.
6. **No `session.started` within 25 s of the SDP answer:** the page POSTs `pause` (so the daemon closes whatever it created), tears down, and shows the error card. SPEC §7.3 does not define this timeout.
7. **A mute survives only a `reconnect`.** After `session.started` on a `reconnect`, the page re-sends `session.input_audio.mute` if the user had muted. A `start` or `resume` begins unmuted.
8. **Auto-connect from `status`:** besides boot, the page connects when a `status` shows `waiting_page` while it is idle, lost or closed (duplicates with `command:"connect"` are ignored). It does **not** auto-connect from the error state, so a failing create (billed 15 s each) is never retried in a loop. Retries need the Try again button, `Space`, or a daemon `connect` command.
9. **Static test exemption:** `icon.svg` has `xmlns="http://www.w3.org/2000/svg"`, which an SVG favicon needs. The "no http(s) URLs" check in `test/web/static.test.js` exempts that namespace identifier only.

## Review fixes (v1 review, 2026-09-23)

These change SPEC behavior. Each has a regression test (`test/daemon/*-review.test.js`, `review-misc.test.js`, and new cases in the hook, toggle and http tests).

1. **Delegation ids are per Live session (§6.9).** Each record stores `live_id`, the sideband id current when it was created. Appends about a record from an earlier session (after resume, reconnect or expiry) use `delegation_id: null`, and a result is framed as `Result for your earlier request "<text>": …`. As a safety net, an `append_failed` for a commentary or thinking append with an id is retried once with `null`. An error that looks like a length error is retried once, split into chunks of half the budget.
2. **Staleness counts only requests that reached Claude.** `current` compares against `sentRev`, the newest record that reached `sent`, not every delegation. A dropped echo gets one silent `thinking` append with its id, so the Live-side delegation is closed.
3. **Stop matching uses `prompt_id` (E6).** Probed on CLI 2.1.281: a message absorbed mid-turn fires UserPromptSubmit with the running turn's `prompt_id`, and a queued message later runs as its own prompt with a new `prompt_id`.
   - Records remember the `prompt_id` of their UserPromptSubmit, and Stop answers the records of its own prompt.
   - A sent-but-undelivered record counts as part of the turn only if the transcript shows it was absorbed. The signal is a `queued_command` attachment or a queue-operation `remove` with reason `absorbed_mid_turn`. The transcript is re-read once after 1.2 s.
   - The 2.5 s `STOP_DEFER_MS` heuristic remains only as the fallback when there is no `prompt_id` or no readable transcript.
4. **Esc (no Stop).** A UserPromptSubmit with a new `prompt_id` ends the previous turn. That turn's delivered records become `interrupted`, a new final status, and `pending-context` is removed. If Stop's POST lost the race, the later Stop revives its record. Records in flight for more than 30 min are orphaned by the liveness sweep.
5. **Busy state.** MessageDisplay no longer sets `claudeBusy`. Hooks whose `prompt_id` has already stopped are ignored for busy. Subagent hooks (`agent_id` present) never touch busy or delivery state. For a subagent, only its permission prompts are announced. An owner switch and voice off reset busy (`resetClaudeState`), and an owner switch removes `pending-context`.
6. **MessageDisplay ordering.** Batches are buffered per `message_id` and assembled by `index` once the final batch and every lower index are in. A batch for a message that is already done, or for a stopped `prompt_id`, is dropped.
7. **Idle close waits for pending work (ARCHITECTURE §7).** It no longer closes while a request is in flight and younger than 30 min.
8. **Reconnect is no longer one-shot.** If no page is listening 4 s later, the daemon opens the window, and it pauses with a notice if no session starts within 30 s. `reconnecting` without a sideband is not "live" for `/talk on`. The page auto-connects when it sees `reconnecting` while idle, including at boot.
9. **Token budget.** Appends are budgeted by an estimate: 1 token per 3 ASCII characters, 1.2 per other BMP character and 2.5 per astral character, capped at 450, not at 1,400 characters. `deliver()` splits thinking and commentary appends that are over budget and clips instructions. `Sideband.append` rejects content estimated above 500 tokens.
10. **Speech redaction.** `speakable()` removes URL userinfo for any scheme, `NAME=value` values when the name looks secret-bearing, labelled passwords and tokens, bearer tokens, and well-known token shapes (`sk-`, `ghp_`, `glpat-`, `xox?-`, `AKIA`, `AIza`, JWTs). It also omits indented code blocks. The Live instructions now say never to speak secrets.
11. **Voice marker nonce.** Each bind gets a 12-hex nonce, sent on the wire as `[sotto voice <nonce>]` and written as the 4th field of `active`. hook.sh matches it anchored at the start of the `prompt` field, and the daemon matches on it too. `voice-context.txt` has an `@MARKER@` placeholder that hook.sh fills in. Verified with the real CLI: an absorbed look-alike without the nonce got no framing, and the nonce message did.
12. **Page credentials (§6.4).** `GET /api/bootstrap` requires either `X-Sotto-Boot: <page secret>` or `X-Sotto-Launch: <code>`.
    - The page secret is persisted in `D/page.secret` (0600).
    - The code is a one-time launch code, valid for 2 minutes, carried in the window URL fragment `#k=`.
    - The response includes `page_secret`, which the page keeps in `sessionStorage` and uses for every later re-bootstrap.
    - macOS shows process arguments to other local users, so the code in Chrome's `--app=` argument is short-lived and single-use.
13. **Daemon shutdown frees the port at once.** After answering `shutdown`, the daemon stops listening and finishes its teardown in the background. `toggle.sh` also waits up to about 4 s for a foreign daemon to go away, not 1.5 s.
14. **Spawn and Node.**
    - toggle.sh spawns the daemon from the plugin root, via `(cd "$ROOT" && exec nohup …)`.
    - The readiness poll allows about 5 s.
    - The daemon exits with code 3 and writes `D/start-error` if Node is older than 22 or has no global WebSocket. toggle.sh reports that as a Node-version error.
15. **Port changes.** The daemon records its port in `D/daemon.port`. If nothing answers on the configured port, toggle.sh looks for our daemon on the recorded port. `off`, `status` and `policy` talk to it there. `on` and `toggle` shut it down and start a new daemon on the new port.
16. **Exit race.** When `/control` gets no answer because the daemon exited in between (an idle daemon exits 3 s after off), toggle.sh treats it as "no daemon" once: `status` and `off` report off, and `on` cold-starts. Found by the `claude -p` probe `/talk off` followed by a bare `/talk`.

## Utterance grouping (2026-09-23)

Observed live: a request spoken over ~30 s with pauses reached Claude as "skill, um. Give you a good design system..."; "Cool. What else should we do to make it better? Also, can we update the UI a bit? Like can we use um the impeccable. Design" was lost. Cause: SPEC §6.9 E3.1 took user fragments only from `offset_ms - 20000`, so anything said more than 20 s before `session.delegation.created` was dropped (never sent, and then skipped by `consumedThroughMs`).

1. **A request is the whole turn:** every user fragment since the previous request was sent (`consumedThroughMs`), bounded to the newest 90 s of session time and 2000 chars (newest words kept, `... ` prefix, `delegation.request` log line with `trimmed_chars`). `collectRequest()` in `daemon/delegation.js`.
2. **Only `input_transcript` fragments are used**, so the Live model's acknowledgements (output_transcript) never leak in. A 1500 ms line that is ≥ 80 % an in-order echo of what the assistant said in the 20 s before that line is left out; `dropped_echo` now also advances `consumedThroughMs`.
3. **Superseded first:** an older record is superseded whenever a newer record exists, checked before the empty/echo checks. With whole-turn requests the newer record's timer can fire first and take all the words, which previously made the older one say "I didn't catch the request".
4. **Trailing-words window:** settle quiet 300 → 600 ms and cap 2000 → 3000 ms (word deltas arrive 200-1200 ms apart in continuous speech). Words after the cap go with the next request, never twice.
5. `Transcript` keeps 1200 fragments (was 400) so 90 s of interleaved speech fits; `isEcho(text, windowMs, atMs)` takes an optional reference time.

Regression tests: `test/daemon/delegation-grouping.test.js` replays the real delta stream.

## Voice switching (feat/voice-switch, 2026-09-23)

The spec sections are updated in place (§3 `prefs.json`, §4.5, §5.7, §5.9, §6.4 `/api/voices` and `/api/voice`, §6.14, §8.1, §8.3, §9). Divergences from v1 behavior:

1. **The voice no longer comes only from userConfig.** `D/prefs.json` (written by `/talk voice <name>`, `sotto voice <name>` or `POST /api/voice`) beats `CLAUDE_PLUGIN_OPTION_VOICE`, which beats `marin`. v1 said the daemon uses the voice "from the latest `/control on`"; it now re-resolves it against `prefs.json` there.
2. **A voice change applies to a live session immediately.** `audio.output.voice` is immutable per Live session, so the daemon closes the session and asks the page to reconnect (reason `voice_change`), which re-creates it seeded with the recent conversation. This reuses the reconnect path but does not count toward its 3-per-10-min limit. The new session greets with `Say only "Switched to <voice>." …` (a `reconnect` otherwise has no greeting).
3. **toggle.sh writes a state file.** With no daemon for this data dir (or a foreign daemon on the port), `/talk voice` lists or writes `D/prefs.json` itself and never spawns a daemon. With our daemon running, the daemon writes it.
4. **Voice requests by speech go through Claude**, not daemon-side detection. Options weighed: (a) regex on the input transcript in the daemon: fragile ("change the voice of this error message"), and it would have to close the Live model's delegation itself; (b) a new sideband tool: the Live API has no client tools besides delegation; (c) delegate to Claude, which runs `bin/sotto voice <name>`: reuses the existing delegation path, Claude resolves ambiguity and asks when unsure, and the CLI is also useful by hand. We chose (c). The Live instructions say the model cannot change its voice and must delegate voice requests; "how to speak" in the do-not-delegate list is narrowed to pace, length and tone. `voice-context.txt` tells Claude about the CLI. In default permission mode Claude Code may ask once to approve `sotto voice …`.
5. **Usage string** is now `sotto: usage: /talk [on|off|status|quiet|milestones|walkthrough|voice [name]]`, and the skill's `argument-hint` matches.
6. **`session.create` log lines carry `voice`.** The e2e test checks that the replacement session was created in the new voice.

## Vocabulary (feat/vocabulary, 2026-09-23)

Spoken skill, plugin and project names are often misheard ("impeccable" as "in peccable"). `daemon/vocabulary.js` adds a glossary.

1. **No API field for keyword biasing.** The gpt-live-1 launch posts mention "keyword biasing", but the Live session schema has no such field. A probe on 2026-09-23 sent `session.start` over the primary WebSocket with each candidate. `session.keywords`, `session.vocabulary`, `session.prompt`, `session.context`, `session.transcription` and `session.audio.input` were all rejected with `unknown_parameter` before any session started, so nothing was billed. The glossary therefore goes into `instructions`, which is also the context the model's own transcripts come from.
2. **§8.1 template:** a `{{vocabulary}}` slot sits between "Do not treat a cough…" and `{{policy_text}}`. With no terms it renders to nothing, so the text is then exactly the v1 template. The six guide headings and the closing lines are unchanged. The glossary text is inserted literally: it is never scanned for placeholders.
3. **Glossary sources and budget:** collection starts when the owner binds (`/control on`), not when the page asks for a session. A cold daemon hit a 200 ms deadline at session start and lost the plugins, while a warm run takes about 50 ms for 357 terms. The scan is read-only and has a 1.5 s deadline. `createSession` reuses a result that is less than 5 minutes old for the same session and folder, and otherwise collects in parallel with the git lookup. Priority order: `<data dir>/vocabulary.txt`, then `<cwd>/.claude/sotto-vocabulary.txt`, then the project name, a non-trivial branch, project skills, top-level folders, `~/.claude/skills` (including skills-dir plugins), and finally enabled plugins with their skills and commands. Enabled plugins come from `installed_plugins.json`, filtered by `enabledPlugins` in the user and project settings. Skills with `user-invocable: false` are left out. Duplicates are merged by alphanumeric key, and the first source wins. The rendered section is capped at 1,500 estimated tokens, and families of 5 or more names sharing a first word collapse to `gws-... (47 names)`.
4. **Owner switch:** the instructions are immutable, so the new project's own names (glossaries, project and folder terms) are sent as one `instructions.append` of 380 tokens at most, after the §8.4 switch instruction.
5. **Delegated prompt annotation (§6.9 E3):** `settle()` may append one line after the user's words (and after the "Replying to…" line): `(Possible names, from speech-recognition matching against the voice glossary, not the user's words: 'in peccable' may be impeccable (skill).)`. The user's words are never changed. The matcher uses the full, uncapped glossary and at most 3 hits. Only mishearings are reported, never a name spoken correctly, so the rules stay conservative:
   - several words that join to exactly a name of 5 or more characters;
   - several words within 1 edit (2 for names of 10 or more characters), or with the same rough sound skeleton, for names of 6 or more characters;
   - a single word within that edit distance or skeleton, only for names of 8 or more characters, and never when one is a prefix of the other ("commits" is not "commit").
   A matcher error never blocks delivery.
6. **§5.8 voice context:** the recognition-errors sentence now says that names are misheard most. It tells Claude to map sound-alikes to the skills, plugins, commands, projects or files it knows, or to a name in a Possible names note, and to say briefly which name it took. The text still contains no `"`, no `\` and no newline.
7. **`/talk vocab` was not added.** It would have needed new toggle.sh parsing and a daemon action. The README documents the glossary file instead. `SOTTO_VOCAB=0` turns the feature off, and the daemon logs one `vocabulary` line per session with the counts, the time taken and the token estimate.

## Spoken notifications (2026-09-23)

SPEC §5.4, §6.10, §6.10.1 and §6.10.2 were updated in place; these are the behavior changes against v1 and why.

1. **Six more forward-only hooks:** Notification, Elicitation, SubagentStop, TaskCompleted, TeammateIdle and PostToolUseFailure go through `hook.sh` like the others (same gate, no stdout; the tests cover the off, non-owner and owner paths for each). PreToolUse already had no matcher, so AskUserQuestion and ExitPlanMode needed no new hook.
2. **Questions are not approvals.** A PermissionRequest for AskUserQuestion/ExitPlanMode no longer says "waiting for your approval to use AskUserQuestion"; the question itself is spoken once, whichever of PreToolUse and PermissionRequest arrives first.
3. **Task notifications are not typed prompts.** Probed on CLI 2.1.281: background completion arrives as a UserPromptSubmit whose prompt is `<task-notification>…`. v1 appended it as "The user typed to Claude Code: <task-notification>…" and spoke its turn as `typed_result`. It now gets a "Background task update" note and its turn is routed by who launched the work (§6.10.1).
4. **SubagentStop carries `agent_id`**, so it is handled before v1's "subagent hooks only show progress" branch. It never touches busy state.
5. **Shorter unrequested speech (§6.10.2).** `typed_result` under milestones is one sentence ≤ 160 chars (was 2 sentences). A Stop whose `prompt_id` never had a UserPromptSubmit (for example, voice turned on mid-turn) is `other_result`: thinking-only unless walkthrough.
6. **Milestones speaks long-running progress:** at most every 30 s, once a turn has run 30 s (v1: thinking only).
7. **Speech queue.** Every commentary waits until the voice is quiet (§6.10.2). Answers to voice requests are never demoted to thinking, even after 20 s: that would lose the answer the user asked for; they go out at the next sentence boundary instead.
8. **Output audio is not a speaking signal.** Measured with the real gpt-live-1 e2e: the sideband's output audio chunks keep arriving while the voice is silent (the last chunk was 42 ms old when the transcript had been quiet for 1.2 s). A first version that used them held a voice answer for 9 s. The sideband still records `lastOutputAudioAt`, and each release logs `speech.send` with `audio_age_ms`, for diagnostics only.
9. **E2E step 8b:** a simulated AskUserQuestion PreToolUse through the real `hook.sh` must produce an acked `commentary.append` with the question and its options.

## Desktop app (feat/desktop-app, 2026-09-23)

SPEC §6.16 is new; §1, §3, §4.1, §4.2, §4.4, §6.12, §11.6 and §12 were updated in place. Changes against v1 and why:

1. **`SOTTO_BROWSER` default is `auto`, not `chrome`** (§4.4, §6.12). `auto` opens the Sotto app on macOS when it is built, else Chrome, else the default browser. `chrome`, `default` and `none` behave as before. The env var still wins over the new userConfig `window` (toggle.sh sends `config.window`; an invalid value is `auto`).
2. **The first `/talk` after install (or after `app/` changes) uses Chrome** while `scripts/build-app.sh` runs detached in the background (about 10 to 20 s of swiftc); the next `/talk` uses the app. A failed build is recorded in `D/app/build.json` and not retried until the sources change. `/control` never waits.
3. **`auto` can open the window about 0.4 s after `/control` answers**: it first runs `Sotto --audio-route` in the background (CoreAudio start-up is slow in a fresh process, so it cannot be synchronous). The reply still says "Opening the voice window."
4. **`auto` prefers Chrome when the system default input is Bluetooth.** Measured: WebKit's capture always goes through Apple's voice-processing unit, which opens the default input first; with AirPods as the default input the AirPods drop to the hands-free profile (48 kHz → 24 kHz) for the whole session, even though the page then picks the built-in mic, and even with `echoCancellation:false`. Chrome, capturing the built-in mic at the same moment, kept them at 48 kHz. `window=app` forces the app anyway.
5. **Echo cancellation in the app is Apple's voice processing, not Chrome's WebRTC AEC** (ARCHITECTURE §6). `getSettings()` reports `echoCancellation: true` and `getCapabilities()` `[true, false]`; `noiseSuppression` and `autoGainControl` are not supported constraints in WebKit. Side effect: while the mic is open, WebKit ducks other audio on the output device by about 15 dB (also with `echoCancellation:false`). With idle sleep and voice wake the page keeps the mic open while sleeping, so in the app the ducking lasts as long as voice is on.
6. **No change to `web/`.** The app injects `app/Resources/bridge.js` at document start. It wraps `EventSource`, `RTCPeerConnection.prototype.createDataChannel` and `getUserMedia` to observe state, and mutes through the page's own `M` hotkey. §6.16 lists the page contracts it relies on.
7. **Hide is transparency, not `orderOut`.** In WKWebView an ordered-out window is a hidden page, and `getUserMedia` in a hidden page never resolved (a 4 s probe timed out, even with the WebKit SPI `_setGetUserMediaRequiresFocus: NO`). A transparent, click-through panel kept `visibilityState` `visible`, and the mic opened in 31 to 44 ms.
8. **Closing the panel does not end voice** (Chrome: closing the window pauses the session). The panel is a floating HUD that the user hides and shows with ⌥⌘T; the menu-bar icon shows that voice is still on. Voice Off (menu) or `/talk off` ends it. Quitting the app unloads the page first, so the session closes as when a Chrome window closes.
9. **The app quits on `close_window`** unless "Stay in Menu Bar When Voice Is Off" is on. Its only jobs need a voice session, which only `/talk` in a Claude session can start.
10. **Launch goes through LaunchServices with a URL**, `open -g -a <bundle> sotto://open?...`: a second request reaches the running instance (`LSMultipleInstancesProhibited`), and `-g` keeps focus in the terminal. `open --args` would be dropped by an already-running instance. A LaunchServices launch delivers the URL before `applicationDidFinishLaunching`, so the app queues it (the launch test caught the crash).
11. **Ad hoc signature with an explicit designated requirement** (`identifier "com.chadboyda.sotto"`). A plain ad hoc signature's requirement is its cdhash, which changes with every rebuild and would invalidate the microphone grant each time. `SOTTO_SIGN_IDENTITY` can sign with a real identity instead.

## Native mic in the desktop app (feat/app-native-mic, 2026-09-24)

SPEC §6.16 gains "Native mic"; the `auto` row of its choice table, the direct-exec line, the bridge's `mic` message, test mode, §11.5 and §12 item 5 were updated in place. Against desktop app deviations 4 to 6:

1. **The app no longer always captures through WebKit** (desktop app deviation 5). On headphones (default output Bluetooth, or the built-in jack with headphones) it captures the chosen input itself with a plain AUHAL input unit: no voice processing, so no Bluetooth hands-free switch, no ducking and no echo cancellation (headphones have no echo path). On speakers, USB, HDMI and AirPlay outputs it keeps WebKit's capture and Apple's AEC. `defaults write com.chadboyda.sotto MicCapture native|webkit|auto` overrides it.
2. **`auto` picks the app with a Bluetooth default input** (desktop app deviation 4) when the app can avoid the hands-free switch: `--audio-route` now reports `output.headphones`, `builtin_input` and `native_mic`, and the chooser returns `{mode:"app", reason:"native_mic"}` when all three hold. Otherwise Chrome as before (an older app build without the fields also gets Chrome).
3. **A second injected script, `app/Resources/mic.js`** (desktop app deviation 6: still no change to `web/`). It answers `getUserMedia`, `enumerateDevices` and `permissions.query` for the page. The device list is the app's (CoreAudio) inputs with labels and opaque ids, so the page's picker and Bluetooth → built-in rule work before WebKit has ever captured; outputs are still WebKit's (unlabelled until WebKit has captured once, so in native mode the speaker picker shows "Speaker 1", …; "System default" works).
4. **Native samples reach the page through `evaluateJavaScript`**, 10 ms chunks of base64 Int16 at 48 kHz, into an AudioWorklet feeding a `MediaStreamAudioDestinationNode`. WebKit has no `MediaStreamTrackGenerator` for audio. The track has the device's label; `getSettings()` reports `echoCancellation:false` and the app's device id.
5. **Route changes are followed without the page's help** where possible: a native capture moves to a new device under the same track; a speakers ↔ headphones switch ends the track and the page re-opens the mic (its existing unplug path). While sleeping with no peer connection that leaves voice wake without a mic until the next connect (known limit).
6. **Test mode mutes the page** (`_setPageMuted:` audio only) so automated live tests never play the model's voice on the user's speakers, and never opens a real microphone natively (fixture WAV or tone).

### Measured (2026-09-24, macOS 26.6.2, WebKit 605.1.15, MacBook Pro mic and speakers; no AirPods connected)
- **WebKit cannot be steered:** there is no API for the capture device of its voice-processing unit or for its ducking. (The hands-free switch itself was measured on 2026-09-23, desktop app deviation 4.)
- **Native voice processing can be bound to one input**, but only when `kAudioOutputUnitProperty_CurrentDevice` is set *after* enabling voice processing: its `VPAUAggregateAudioDevice` then contained only the chosen input (ZoomAudioDevice, while the default input was the built-in mic); set before, it contained the default input. AVAudioEngine still created an idle default-device aggregate. Voice processing cancels only what it plays itself, so using it would mean playing the model's voice natively too; not built.
- **AUHAL on the built-in mic** (real device, 1.5 s, from a terminal-run probe): 47.5 kHz effective, 10 ms drain chunks, drain lag at most 10.4 ms. The 44.1 → 48 kHz converter path produced 47 982 frames per second of input.
- **App → page latency** (native, live session): transport (native timestamp to the page) 0.1 to 0.6 ms mean, p95 at most 2 ms; worklet queue 20 ms steady after the trim (54 ms before it: a start-up backlog never drained), no underruns, no drops. `getUserMedia` resolves in about 20 ms. Added capture latency over the hardware: about 5 ms average chunking plus about 20 ms of queue.
- **gpt-live-1 hears the native mic:** the TTS fixture through the app's own capture was transcribed ("Hey Can you ask Claude what files…") and live 1.6 s after `/control on`. One of four live runs failed before that with "Timed out while gathering network candidates" (WebRTC ICE, not the mic); the rerun passed.
- **Self-interruption without AEC (simulated):** the model's own voice mixed back into the native mic 40 ms later, at -10 dB (echo peak -27 dBFS in the mic) and at 0 dB (-16 dBFS, as loud as the user's speech). Both times gpt-live-1 spoke a long answer through to the end (57 and 61 of 78 words, paraphrased as usual), transcribed none of it as user speech, and created no extra delegation. A pure delayed copy is the easiest echo to reject; real speakers add reverb and distortion, so speakers keep AEC.

New contract in SPEC §6.17 (self-update), with changes to §4.4, §5.7, §5.9, §6.2, §6.4, §9.1, §9.2 and §11.6. Divergences from what the spec said before:

1. **The daemon restarts itself** when its sources change (§6.2 said it runs until off, shutdown or owner death). Only at a quiet moment (sleeping, paused, or 45 s of silence while live, nothing pending for Claude), after a preflight load of the new code, and never twice on the same failing code. `SOTTO_UPDATE=0` turns it off.
2. **The single-instance rule has one exception:** a successor started with `--handover` accepts the pid file naming its predecessor, and keeps `D/active` and `pending-context` (§6.2 said a starting daemon always deletes them). Same `daemon.key`, same page token, same marker nonce: nothing the hooks, toggle.sh or the page hold goes stale.
3. **The state crosses processes over a pipe.** The handover holds the inbox token (in memory only, per the secrets rule); it goes to the successor's stdin and nowhere else. The successor's stderr goes to `D/logs/successor.err` (new file) so a failed start can be logged.
4. **`/api/session` can answer 503 `restarting`** for the moment between closing the old session and the swap; the page treats it as "wait", not as an error.
5. **The page reloads itself** after a restart that changed `web/` (§7.2 had no reload). `/api/bootstrap` gains `build`. The reload drops `autostart` from the query so it never starts a session by itself.
6. **`/talk restart`** is a new action (usage string, argument hint, `/control` action, CLI `sotto restart`).
7. **Runtime:** toggle.sh now checks `node -v` before a cold start (measured 10 ms plain, 140 ms through a nodenv shim; only cold starts pay) and falls back to Bun ≥ 1.1 (`bun`, then `~/.bun/bin/bun`). Before, an old Node was only caught after the spawn, through `D/start-error` (still there for `SOTTO_NODE`). The "no node" string of §9.1 became four strings that say how to install one. Bun 1.3.5 passed the full smoke e2e (43/43), the self-update e2e and the process-swap unit tests unchanged; `bun test` is not used (the unit tests stay on `node --test`).
8. **Spoken cue:** the first session after a restart from `live` says only "I just updated myself." (`updateGreeting`, §8.3 has a new greeting). From sleeping or paused nothing is spoken; the page shows a notice (code `updated`).

## Decisions reach Claude (fix/voice-decisions, 2026-09-24)

SPEC §4.1, §5.8, §6.9, §6.10, §8.1 and §8.2 were updated in place and §6.10.3 and §6.18 are new; these are the behavior changes against v1 and why.

1. **Evidence.** In the 2026-09-23 session log, gpt-live-1 answered utterances Claude needed without delegating them: the project name ("Sotto is a clever name", then "I thought we picked Sotto / did we not agree on that"), "I agree with you, the public repo is fine …", "I'm fine keeping the private repo, but make this available to other people", "let me know when you auto restart", "why did that get cut off? that seems like a bug", "switch the voice to Shimmer". It also claimed things it had not done: "I'll mark Sato as your pick", "I'll tell you when that's live", "I'm having Claude Code check the log", "You're hearing Shimmer now". v1 only carried such words to Claude inside the next request, and only within 90 s of it.
2. **Instructions (§8.1).** "Delegate to the backend when" adds decisions, preferences, agreement, approvals, picks, answers to Claude's questions, feedback, bug reports, corrections, casual requests ("let me know when…") and "When in doubt, delegate." "Do not delegate" narrows small talk to *only* small talk and the "answer from the conversation" case to when nothing is being decided or asked. A new paragraph forbids claiming to have noted, recorded, marked, saved, scheduled, started or told Claude anything without a delegation, and promising later updates; the model says "I'll pass that to Claude" and delegates. The voice-switch bullet says only the user's own clear request changes the voice. Measured with the real model (test/e2e/decisions.mjs): with the v1 instructions it answered "Sotto is a clever name. I think we should go with that one." itself ("I like it too … I'm good to go with that"); with the new ones it delegated both test utterances within 0.6 s of the last word.
3. **Transcript mirror (§6.18, new).** Undelegated user speech reaches Claude 6 s after the user stops, as `[sotto voice <nonce>] (said to the voice assistant, not delegated) <words>`, inbox priority `later`, minus filler, voice-only commands, short fragments and echoes. Words are never sent twice (the mirror advances the delegation watermark before it writes). userConfig `mirror` (`all` default, `decisions`, `off`) and env `SOTTO_MIRROR`. Known trade-off: while Claude is busy, a `later` mirror can be read after a `next` request the user made right after it.
4. **Late delegation (§6.9 E3.2).** A delegation whose words the mirror already sent was `dropped_empty` ("I didn't catch the request"); it now sends them again as the request, quoted, so Claude answers and the answer is spoken; if Claude already picked the mirror up, the record becomes `mirrored` (new final status, page label "Already with Claude") and the model is told the answer is on its way, so Claude does not answer twice.
5. **Voice context (§5.8).** Explains the mirror tag (act on decisions, answers, feedback and casual requests; answer project questions; ignore small talk; reply only "Noted." otherwise), and restricts `sotto voice` to the user's own clear request. Mirror turns route as `mirror_result` (§6.10): "Noted." becomes a silent note, anything else is spoken briefly under every policy.
6. **Claude awaiting input (§6.10.3, new).** A Stop whose last message ends in a question or an option list, or an AskUserQuestion, sends a silent note that Claude is waiting and that the answer is a decision to delegate; the seed repeats it after a reconnect or wake; the next UserPromptSubmit clears it. `/status` has `claude.awaiting_input`.
7. **No idle nag after a mirror turn.** A `mirror_result` counts as spoken for the idle period, so Claude's `idle_prompt` after a "Noted." turn is not announced.
8. **Status and counters.** `/status` `config.mirror`; counters `mirror_sent`, `mirror_failed`; logs `mirror.send`, `claude.awaiting`; `inbox.send` logs its priority.

## Round 2 fixes (fix/round2, 2026-09-24)

SPEC §3, §6.4, §6.10.2, §6.14, §6.14.1 (new) and §8.2 were updated in place. Changes against the earlier behavior and why:

1. **The seed is several messages** (§8.2). The voice history of a resume/reconnect/switch goes in as real `user` / `assistant` messages (plus a developer note before and an end marker after), not as "You said: …" lines inside the developer message. Observed live: after a voice switch the new session spoke the last update again. The seed budget is now an estimated 7,000 tokens for the whole list (API: 8,192 combined, 128 messages), not 24,000 characters.
2. **Speech queue across session swaps** (§6.10.2). The queue is suspended while a switch, reconnect or expiry replaces the session; held items wait for the new session (before, they fell into `pendingResult`, where only the last survived and the seed handed it over as "a result that arrived while paused"). The last commentary is carried over only if no output speech followed it. Text already spoken is not queued again within 20 s of a swap.
3. **Voice switch waits for `session.closed` (up to 2 s) before asking the page to reconnect** (§6.14). Sending `session.close` and the reconnect command at the same moment made the server close the old session as `connection_lost` / `remote_hangup`: the page tore down the peer before the close was processed. Measured wait in the e2e: about 0.7 s.
4. **Voice samples** (§6.14.1, new route `GET /api/voice-preview`, new cache `D/voice-previews/`). A primary-WebSocket session per voice, not the WebRTC path: WebRTC bills 15 s at creation, a WebSocket bills per second (2-5 s per sample). Measured over 34 real sessions: without input audio the model never speaks, so silence is streamed; in about 1 of 8 sessions the model stays silent anyway, and a nudge at 3 s rescued some of them but not all, hence the close-and-retry at 5.5 s. First-play latency: median 4.7 s, p90 10.6 s (a retry), cached about 5 ms. The alternative, OpenAI TTS, was rejected: it lacks most Live voices and would not sound like the session.
5. **Wall-clock tests scale with machine load.** Timing bounds in `test/scripts/hook.test.js` and `toggle.test.js` add an allowance measured from bare `/bin/bash` and `node` spawns (`spawnBaseline()`), the gate check's thresholds scale with the bare-script quartile, and it gets 5 measurement rounds; `waitFor` defaults are 8 s (they return early). The vocabulary content test uses a 10 s deadline (the deadline itself has its own test). `http.test.js` and `window.test.js` bounds were raised to 2 s and 3 s; they only prove that nothing waits for a 15 s close or a 20 s build. Verified: `npm test` passed 8 runs in a row next to a 36-thread CPU burner.

## Signed app release (feat/signed-release, 2026-09-24)

SPEC §6.16 gains "Release download" and "Release"; §3 (files), §4.4 (env) and §11.5 were updated in place. Version 0.2.0.

1. **The app is downloaded before it is built.** When the bundle is `missing` or `stale`, the daemon runs `daemon/appfetch.js` detached instead of `build-app.sh`. It installs the notarized release of the plugin's version from GitHub and runs `build-app.sh` itself only when that fails. Users no longer need Xcode or the Command Line Tools. `failed` (a local build of these sources failed, not retried) now also gets a download try, without a build.
2. **A release is used only when it was built from the same `app/` sources** (`Contents/Resources/sotto-source.json` against the plugin's sources hash, the same hash `build.json` uses). A clone with an edited `app/`, or a plugin version whose release was cut from another commit, builds locally. This mismatch is recorded as final for that version and hash, so it costs one download.
3. **Trust comes from the signature, not the checksum.** The `.sha256` file is fetched from the same release as the zip, so it only catches corruption. `codesign --verify --deep --strict` with a requirement pinned to Developer ID + team 6M6D2W72ZB + the bundle id, and `spctl` reporting `Notarized Developer ID`, reject tampered or foreign bundles (a one-byte change to a resource of the real notarized bundle fails with "a sealed resource is missing or invalid"). `stapler validate` is not used on the user's side: `xcrun` would prompt to install the developer tools, which is what this feature avoids; `spctl` accepts the stapled ticket offline.
4. **Downloads carry no quarantine attribute** (Node's `fetch`, not a browser), so macOS does not run its own first-launch Gatekeeper check; the `spctl` assessment above is that check, done before the bundle is moved into place.
5. **Retry policy:** one attempt per plugin version and sources hash; failures other than a sources mismatch (404 before the release is uploaded, network, signature) retry after 24 h. `SOTTO_APP_DOWNLOAD=0` disables the download; `SOTTO_RELEASE_BASE` points it at another server (tests).
6. **Signed builds use the hardened runtime** with one entitlement, `com.apple.security.device.audio-input` (no sandbox, JIT or library-validation exceptions: WKWebView's JIT runs in WebKit's own processes). Ad hoc local builds are unchanged, so the microphone grant of an existing local build survives rebuilds; switching to the Developer ID build changes the designated requirement, and macOS asks for the microphone once more.
7. **Version 0.2.0 everywhere** (`package.json`, `plugin.json`, `app/Info.plist`, `daemon/config.js` VERSION, the SPEC examples); `test/scripts/app-static.test.js` checks they agree, and `release-app.sh` refuses a version that differs.
